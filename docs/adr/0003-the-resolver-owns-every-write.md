# The Resolver owns every write, and the gate is on its own tools

PLAN.md section 5 puts `interruptOn` on `propose_data_fix`, `create_pull_request`, and `send_customer_reply`. Two of those are the Resolver's; `propose_data_fix` is the Data Investigator's, and gating it there would be wrong in two ways. The Resolver decides only after all three Investigators have reported, so a Proposal raised mid-investigation would put a Reviewer in front of a fix before the Evidence for it was in. And an approved fix has to run somewhere: `propose_data_fix` is defined never to execute, so approving it would let the run continue with nothing changed and a Verdict that says otherwise.

So the Data Investigator keeps `propose_data_fix` unchanged — it parses the statement, applies the tenant scope, counts the rows it matches, and hands back a Proposal — and the Resolver gets a write tool of its own, `apply_data_fix`, which is the one behind the gate. The timeline then reads as it happened: an Investigator proposed, the Resolver decided, a Reviewer approved, and the row changed. `send_customer_reply` is the Resolver's as planned; `create_pull_request` is configured in the same gate and arrives with the Fix Shipper.

One narrowing goes with this. `send_customer_reply` is gated for customer Tickets only. CONTEXT.md says a tester's or Sentinel's Reply is an internal note that is never sent anywhere — it is read off the closed Ticket — so there is no outward write for a Reviewer to hold, and holding one would put a second click in front of every internal Ticket for nothing. PLAN.md section 5 states the policy without a Source condition, so this is a deliberate reading of it rather than what it says; a Reply that is genuinely delivered must be gated whatever its Source, and the day delivery stops being a stub the condition in `interruptsFor` has to go.

`create_pull_request` arrived with the Fix Shipper, and it split that subagent's job in two. PLAN.md section 4 gives the Fix Shipper the whole of shipping: push the branch and open the pull request. But a subagent's tool call is not what the Resolver's `interruptOn` holds — the gate is on the orchestrator's own tools — so a `create_pull_request` inside the Fix Shipper would be a write that reached GitHub with nobody asked. The split follows the risk rather than the agent boundary: pushing a branch nobody has been asked to merge changes nothing anyone reads, so the Fix Shipper does it unheld, and the pull request against ShopLite's default branch is the Resolver's own gated call. What the card then shows is complete — the branch exists, the files are on it, and the body is the RCA — which is a better Proposal to review than an intention to push.

The call that reaches GitHub is the agent package's, since only the run holds its MCP client; what the portal injects is what happens with the result. It writes it onto the approval and puts the link on the Ticket as an internal note, because a customer's Reply says a fix is underway and never carries a link to the repository.

The three write tools are the only tools of the Resolver's that change anything, and their bodies are injected. The portal supplies effects that run the fix through a role with no privilege but UPDATE and DELETE on the ShopLite schema, in one transaction, under the row cap, with the rows as they were written onto the approval. The command line supplies effects that write nothing: with nobody watching, it rejects both a data fix and a pull request with a reason the Resolver acts on, because approving a write from a shell is the thing the gate exists to prevent. It does approve a Reply, since delivering one is a stub that logs and the Reporter reads it off the closed Ticket; refusing that would only stop a run finishing without protecting anything. The agent package never touches ShopLite data itself.

## One tool beside them, added later

`escalate_to_human` is the Resolver's fourth tool and is not gated. It writes nothing: it records that this Ticket needs a person, and the run then returns its Verdict as usual. Gating it would be a Reviewer approving being asked, which is the one thing that needs no approval — the cost of an escalation is a Reporter's wait, not a change to their data, and a run held at the gate on it could not be escalated by the Reviewer holding it.

It is not advice, though. Once a run has called it the Ticket is escalated whatever Outcome the Verdict then claims, and the holding message replaces whatever Reply the model wrote, the same way a Verdict below the Confidence threshold is escalated in code. Both rules live in `@incident-resolver/shared` and are applied twice: where the agent package reports a run's Verdict, and again where the portal closes a Ticket on one. The second is not belt and braces — the portal is what tells a Reporter how their Ticket ended, and any Resolver behind that seam, the scripted one included, must be held to the same rule.
